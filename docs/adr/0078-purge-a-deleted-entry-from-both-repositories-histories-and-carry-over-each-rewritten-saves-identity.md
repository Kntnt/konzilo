# ADR 0078: Purge a deleted entry from both repositories' histories, and carry over each rewritten save's identity

**Date:** 2026-11-26 · **Status:** Accepted. Settled by Thomas in triage on 2026-11-25 (spec #106): only an Admin purges, from the *Deleted* page, and an Editor sees no way to; a purge is confirmed in several steps, each saying that it is meant and that there is no way back, and that backups keep what is purged until they expire, the last way back until then; before it starts, the Admin sees who has which form open and chooses to run anyway, those tabs warned and reloaded, or to wait until they are done, while nobody may open a form; no save is taken while it runs, and every tab open in the editor reloads afterwards; every save after the oldest one rewritten gets a new identity, and everything that names a save by its identity is carried over. The rest is a technical choice; Thomas may veto, among them, chosen in building it on 2026-11-26:

- **How the history is rewritten:** both repositories are cloned anew, bare, and each branch `main` is read by Git's `fast-export`, without the files' contents, and written again by `fast-import`, every commit with its author, its committer, their moments and its message, what is purged left out and what changes changed (`src/purge/rewrite.js`). So each commit before the oldest that changes keeps its identity, and a commit that held nothing but what is purged goes, its children following its parent; one that was empty before, or joins two lines, stays. The rewrite is handed what to remove, a file a commit writes, which it may judge by what the commit held, and what to change, a file's bytes, so that the purge of a passage from every old revision (#117) rewrites alike. A signed commit loses its signature, as `fast-export` drops it; Forgejo signs none here.
- **What goes from the source:** every revision of the entry's file; for an image library entry, each original any revision of it named, unless another library entry, in any revision, deleted or not, or a file as the branch stands names it, by `media/<name>` as written or as a URL writes it; and in every revision of `redirects.json`, each rule that leads to the post or term by its key, `<language>/<ID>` on a site in several languages, or by its bare ID, which leads to whichever translation there is, where no other translation of it stands at the head, or comes from or leads to an address it had, its own other addresses among them.
- **What goes from the content repository:** each file the content ledger said was the post's in the commit that wrote it, by every path the ledger ever gave it, and not another post's that later took the same path; a term's page file by each slug the term had, where no other term of the source commit the content commit publishes had that slug; each master made of an original that goes, by the original's hash in its name; the entry's own entries in every revision of `.post-ids.json`, with an Admin's file named by the hash of its new version where the purge changed it; and in every revision of `redirects.json`, the rules from or to an address it had. Its commits name the source commit they publish by its new identity.
- **How others' saves are kept:** each push carries a lease on the head the purge read, and the source's carries the record's branch with it, atomically; a save that came meanwhile turns it away, and the purge starts again from what is there, at most four times, losing nothing of that save. While it waits and runs, and while it is unfinished, the service shuts every form, so that the editor takes no save: a tab's hold of a form is answered `423` with the purge, the form opens read-only with the way back to the list, and a save, a deletion and a restore are refused, saying so, and saying whether the purge waits, is under way or is unfinished. A new entry, which has no lock, is refused at its save by the purge the locks tell, as is a rule made on the *Addresses not found* page; and the feed reader reads no feed and saves nothing, and reads what came meanwhile once the purge has ended, as each of its saves would start the purge again. A push from outside Konzilo, which nothing here stops, makes the purge start again too, but one that lands in the minutes Forgejo is collecting what went, with `git gc --prune=now`, could be lost: whoever runs the site does not push to the source while a purge runs. A builder's build and the purge never run together: the purge's program marks that it holds the builds back, then waits for the builder's mark of a build that runs to go; the builder marks that it builds, then looks for the purge's.
- **Which program holds the instance credential and runs the purge:** a program of its own, `konzilo-purge`, in a Compose service of its own, `purge`, with a token of the instance's account, `konzilo`, that may write repositories and run Forgejo's own tasks, which the seed makes into the volume `purge-secret` that nothing else mounts. It runs nothing of the site's code, has no port, and takes nothing from outside but the purge the service asks for, written into a folder only the two of them mount (`purge-control`), where it says how the purge stands and how far it has come. The builder, which runs the site's code and its dependencies, and the service, which answers the internet, hold no such credential, and the builder cannot ask for a purge, as it mounts no such folder: the folder it shares with the purge's program (`build-control`) holds only the marks by which a purge and a build never run together, the build request and the build log. A purge's name, which names the program's folder for it, is checked before it does.
- **How Forgejo lets go of what went:** Forgejo's own `git_gc_repos`, which `compose.yaml` gives `git gc --prune=now`, and `gc.reflogExpireUnreachable = now`, so that the log of the branch's moves that a rewrite leaves no longer holds the old commits; and `gc_lfs`, which removes an LFS object no object of the repository names, given that it came at least a minute before, so that an upload whose commit is on its way is never taken. No schedule runs them; the purge asks for each, again every 15 seconds, until Forgejo answers for none of the commits that went, the head that was and each save that held nothing else, and for none of the LFS objects that went, for five minutes at most; then `delete_repo_archives`. A purge that runs out of that time, or whose archives Forgejo does not remove, is unfinished, and is finished as below.
- **How identities are carried over:** a branch of its own in the source repository, `konzilo-purges`, holds the record of purges, `purges.json` (`src/purge/record.js`): by each rewritten save's new identity, the push that brought it as it was, its account and moment, or none where Forgejo had no record of its account. A rewritten save is pushed anew by the instance's account, so its push in Forgejo's feed is the purge's; the service's History and *Deleted* page, and the builder's role check, read the record first and the feed after. Forgejo keeps the branch to the instance's account alone by a branch protection the seed makes at every start, which holds for the name whether or not the branch is there yet, so nobody who edits can make it say anything. It is in the repository, so it moves with the history as an archive moves a site (ADR 0006). A push whose commits Forgejo can no longer list, as one the purge took the head it started from of, brought none of what the history still has.
- **A purge stopped or broken after its first push:** the purge's program records each step it takes in `purge-control`, `purge-progress.json`: what it is to push, with what the steps after need, before it pushes, then the source pushed, the content pushed, what went let go by Forgejo, its archives removed and the build log without what went; the service forgets what the purge took once the program says it is done, and says so in the state. A purge that pushed the source and then stopped or broke is unfinished: its clones stay in `purge-work`, the builds stay held back, no other purge is made, and every form stays shut, also across a restart of either program, as the history is half rewritten. The *Deleted* page and the *Purge a passage* page tell an Admin so, with *Finish the purge*, which asks the program, by the purge's name alone, to go on from the first step it had not taken, as the purge was asked for, the passage kept for it until it is done; every tab that saw the purge reloads once it is. A program stopped between its source push and saying so learns it from the record's branch, which stands where the purge put it. The content push is tried four times, a second longer each time, in a run and in the run that finishes it; one a run before made is done, and one where the content repository stands elsewhere is not tried, as nothing but a build writes it. A purge whose clones are lost before it is finished stays unfinished, for whoever runs the site.
- **The builder's record and its release, and the clones:** the builder, the live preview and the service hold no clone past a purge. The builder learns of one by the record's branch moving, drops both its checkouts and takes them anew, and makes a release of its own, though nothing a visitor sees changed, with no release from before beside it, which may hold what went; the record then names the new head and the new release. The live preview drops its checkout and its content folder and starts again, at once as it starts and within half a minute of a purge while it runs. The service forgets its small pictures, and learns the history anew, which it does by itself (ADR 0077). The purge's own clones go once it is done, or refused, or broken before its first push. The build log loses each line that names a file that went.
- **How others' tabs are told:** with the locks, which every tab in the editor asks for. Run anyway: each tab that has a form open is told to reload, says so in a dialog, and reloads after ten seconds, or at once where the Editor says so; the purge runs once those tabs have let their forms go, or after twenty seconds, letting go what they still hold. Wait: the purge runs once no form is open, and an Admin may stop waiting. Every tab that saw the purge wait or run reloads once it is done; a tab loaded after it does not. A purge that waits is kept in the service's memory beside the locks, so a restart forgets it; one asked of the purge's program is taken back from the request it wrote. A purge whose program does not say within half an hour that it has ended is given up on: its request is taken back, so that the program does not make it with the forms open, and the forms open again, unless the program pushed the source, which leaves the purge unfinished. The program takes back only the request it made, so that one asked for since stays, and one that ends after all is forgotten as any that is done, and told an Admin who asked.
- **A note of itself:** the record lists each purge, who and when, with nothing of what, and an Admin reads on the *Deleted* page how many there were, and the last by whom and when.
- **The steps:** *Purge for good…* on each row and on an entry read, for an Admin; then what goes, that there is no way back and what the backups keep, and *I mean it: go on*; then the entry's name written to confirm it, with the same words; then who has which form open, or that no one has, with *Run anyway* and *Wait until they are done*, or *Purge for good now*; then how it stands until it has ended. Each step is in the browser's own dialog, its heading taking the focus, what changes said to a screen reader. In Swedish, *Rensa för gott*, kept apart from *Återställ*.

Settled by Thomas the same day for a passage (#117): only an Admin purges one, with the same steps; the Admin types the passage and sees every post, term, menu, setting and image library entry, and every revision of each, that holds it, with the text around it; the purge refuses while a current version holds it and names each, which the Admin takes it out of by hand and saves as usual, so that an editor sees the published text change; then it goes from every old revision with no marker in its place; others' open forms are handled as for an entry. Technical choices Thomas may veto, chosen in building it on 2026-11-26:

- **How a passage is found:** in the text as written, case-insensitively, a run of whitespace in it matching any run of whitespace, a line break as JSON writes it, `\n`, and Markdown's hard one, a backslash at a line's end, among them; and any of its characters after the escape Markdown, YAML or JSON may write before it, a backslash before ASCII punctuation, and before any character but the first the empty comment `<!-- -->` that Markdown's fallback splits an address with (`content-format.md`, *Escapes and fallbacks*), so that `ebba@example.com` is found in `ebba<!-- -->@example.com`. What is found goes whole, its escapes with it, and again where taking it out joins it anew. A passage is trimmed, each run of whitespace in it one space, and has 3 to 500 characters (`src/purge/passage.js`).
- **Where it is looked for:** every file of the source in every revision of `main`, but an image's below `media/`, an LFS pointer, and anything that is not UTF-8 or holds a NUL; and every save's message, which a save made outside the editor, such as an author's added from the form, may name it by. Not a file's name, which in the source is an ID.
- **Who looks:** the purge's program, in the source cloned anew, and in the content repository's head, fetched alone, which it removes once it has looked, as the service holds no clone and Forgejo's API reads no file of every revision at once. The service asks it in `purge-control`, `passage-search.json`, and reads its answer from `passage-found.json`, each taken as soon as it is read, as each holds the passage or the text around it; it waits a minute at most, one search at a time, and answers a search while a purge runs that it is busy. The passage goes in the body of a `POST` to `/_konzilo/purge/search`, never in an address, which logs keep.
- **What an Admin is shown:** the files whose current version holds it first, then the others by their newest revision that does; each file's revisions newest first, twenty at most and how many more, each with its moment, the commit's own, the current one marked, and the text around the first three places in it, sixty characters on each side, up to the place before and after; a hundred files at most, and the twenty newest saves whose message names it. A file is named by its form, a post, a term or an image library entry by what it is called where the editor knows it, a menu and the settings by their form, and linked to its form where it can be opened, as one whose current version holds it always can.
- **What goes:** from the source's history, every version of every file it was found in, and every message; from the content repository's, every content file of an old revision and every message that holds it, as each is built from the source, but never a file of its head, which is the published text, and changes only by an editor's save the build publishes. Each line of a message is left without the space taking it out leaves at its end. The build log loses each line that holds it.
- **Every save stays:** a save that changes nothing once the passage is gone, such as the Admin's that took out nothing else, stays as a save of nothing, at its moment and by its account, rather than go as a save that held nothing but a purged entry does; it no longer shows in a form's History, as it changes nothing there.
- **When it is refused:** the purge's program looks at the current version of every file as it purges, and refuses, naming each file, `current`, where one holds it; `published`, where a file of the content repository's head does, as one the build has not yet made again from the Admin's save, or a refused post's last one, which keeps it until a save of the post is published; and `not-found` where neither history does. The page offers no purge while a search shows a current version that holds it, and names each with a link to its form, nor while it shows a published file that does, which the search reads in the content repository's head and names by its path, and the purge's refusal names each file as the page does.
- **The page:** *Purge a passage*, in Swedish *Rensa textavsnitt*, beside the *Deleted* page, on every site, which an Editor reads is an Admin's and finds nothing on. The steps are the entry's, the passage written again to confirm it, compared whatever its case and its whitespace. Once the tab has loaded again, the page says how many revisions in how many files and how many saves' messages were changed, from the purge the tab asked for, by its name, and nothing of the passage; the service keeps the passage only until it has asked the purge's program, and tells no one it. While a purge waits, runs or is unfinished, each tab is told so, whatever it takes.

## Decision

- **A purge removes a deleted post, term or image library entry for good:** every revision of its source file, every content file the builds made from it, the rules that led to it and the site's rules from or to any address it had (ADR 0036), and, for an image library entry, its original and the masters made of it, unless another entry or a current file names the same original (ADR 0055). Only a deleted entry is purged; one that is not is deleted first, as a save.
- **Nothing of it is left to fetch:** Forgejo holds no object, LFS file or other ref that reaches it, a commit that went is in no answer of the service (ADR 0074) and in no list of the *Deleted* page (ADR 0077), and a build follows, so that the release in use holds nothing of it.
- **Every save after the oldest one rewritten gets a new identity,** and whoever pushed it, as the role check and the History read it (ADR 0008), the builder's record and release, the content repository's commits, the live preview's timeline and every clone are carried over, so that everything reads as before but for what was purged.
- **Only an Admin purges,** by the instance's credential (ADR 0007), confirmed in several steps, choosing what becomes of the forms others have open.
- **A passage is purged too,** such as a person's name and telephone number: an Admin finds every file and revision of the source that holds it, the current versions first, takes it out of each current version by hand and saves, and then purges it from every old revision of both repositories, and from every save's message, with nothing in its place. The purge refuses while a current version holds it, or the published text does, and changes no current version of the source, nor the content repository's head.
- **The backups are the hosting layer's,** and keep what is purged until they expire; the purge's words say so.

## Why

- A deleted entry stays in the history so that it can be restored (ADR 0077); a purge is for what must not stay, such as personal data, and only a rewrite of the history takes it from there.
- Carrying over who pushed each save keeps the role check and the History true: without it, every rewritten save would read as the instance's own.
- Holding the credential that can rewrite everything in a program that runs nothing else keeps it from the site's code and from what answers the internet.
- Asking Forgejo for what went until it answers for none of it proves the purge, rather than trusting a task that runs in the background.
- A passage in an entry that stays, such as a name in a post still published, cannot be purged as an entry is. Taking it out of the current version by hand first leaves the published text to an editor's save, which the History and the publish status show as any other, and leaves the purge nothing to change but what no one reads unless they look back.
- Finding a passage as written, through the escapes written into it, finds it as the Admin sees it in the form, where Markdown's backslashes and JSON's quoting are not shown.

## Considered and rejected

- **`git filter-repo`.** It needs Python, which the image does not hold, and would hand back no map of old identities to new.
- **`git filter-branch`.** It runs a command for each commit, slowly, and has Git warn against it.
- **The record of pushes beside the history, in a volume.** It would not move with the repository, and the service and the builder would each have to be trusted to keep it.
- **Git notes, or a ref outside `refs/heads`.** Forgejo protects branches alone, so nobody who writes could be kept from a note, and its API reads only one notes ref, a commit at a time.
- **The builder purging.** It runs the site's code and its dependencies, which would then hold the instance's credential.
- **Removing what is purged from Forgejo's activity feed.** Forgejo has no way to change one push's record, and the feed is what names who pushed every save no purge rewrote.
- **A passage purged from the current versions too.** The published text would change with no save of an editor's, and nothing in a form would show it.
- **A passage purged from the content repository's head,** where a build has not yet published the Admin's save, or a post's last accepted version holds it after the build refused a newer one. That too would change the published text with no save of an editor's, which the purge leaves to the editor.
- **A marker where a passage was,** such as `[removed]`. It would say that something was there, and where.
- **A search by Forgejo's API, or by its code search.** The API reads one file at one commit at a time, and the code search reads the branch as it stands alone.

## Consequences

- The activity feed keeps what Forgejo wrote of each push: up to five of the commits it brought, each with its message, which for an upload names the file. A purge cannot reach it.
- A purge rewrites the history of both repositories, so a clone anyone keeps outside the site's own programs still holds what went until it is made anew.
- A passage's purge hands the rewrite what to change, and shares the record, the steps and the handling of open forms with an entry's (`src/purge/histories.js`).
- A passage is not found where it is not written as the Admin types it: split by markup, as `**Ebba** Svensson`, in another case of a letter that changes as `ß` does, or in another Unicode normal form. Nor in a file's name: in the content repository a post's file and old addresses are named by its slug, which a passage in its title may have given it.
- The activity feed keeps the messages of the saves a push brought, which a passage's purge cannot reach either.
