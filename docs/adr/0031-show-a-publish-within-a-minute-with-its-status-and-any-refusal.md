# ADR 0031: Show a publish within a minute, with its status and any refusal

**Date:** 2026-10-27, amended 2026-11-13, 2026-11-25 and 2026-11-26 · **Status:** Accepted, settled by Thomas on 2026-10-27: a publish shows on the site within about a minute; the post shows whether it is being published, is live or failed; a refusal is explained to the editor and alerts Kntnt; scheduled publishing works. The rest is a technical choice; Thomas may veto. Settled on 2026-11-13, as a technical choice Thomas may veto: a start installs the site's dependencies only when what they are installed from has changed, by a record in the copy's `node_modules`. Settled by Thomas on 2026-11-25: a command the builder waits for has a time limit, ten minutes by default, the suite's, which an operator can change as a setting; a build whose command is stopped for taking too long is tried once more by the builder itself, since the deadlock that holds it up comes by chance; and a build stopped again is recorded as failed, the site staying on its release until the next save. Chosen on 2026-11-26, as technical choices Thomas may veto: the module every Node the builder starts loads first is the core's `src/node-exit.js`, which a run of the suite loads too, in place of a file of its own ([ADR 0014](0014-test-at-two-seams-and-keep-the-acceptance-suite-small.md)); the setting is `KONZILO_COMMAND_TIME_LIMIT`, read with the peers and folders ([ADR 0002](0002-let-the-core-know-one-site-and-run-it-everywhere-with-docker-compose.md)), in whole minutes or seconds, `10m` or `90s`, and no longer than a timer holds, some 24 days; the limit holds for each command apart, not for the build as a whole, and for the search documents too, whose stop leaves the release live and `unindexed`, with no second try; a command runs as a process group of its own, stopped whole by `SIGKILL`; the site's build clears its `dist/` before it runs; what a stopped intake wrote is undone, the content checkout put back to its last commit; a confirmed deletion's code holds for both tries; the build's line says `retried`, with the stopped command's words; and the builder's own install and the editor's configuration at its start load the module too.

## Decision

- **`status` is one field,** as a form of draft, scheduled with a date and time, and published. New entries are drafts.
- **What starts a build.** Saving makes a commit. Forgejo's webhook makes the service write the build request. A check every minute catches a lost webhook, since Forgejo does not retry.
- **One build at a time per site,** and publishes during a build give one more build, not a queue. A failed build has taken its request, and does not start again by itself, but for one whose command took too long, which runs once more at once (below).
- **A build's steps:** lock, intake, commit in the content repository, Astro, web server files, switch `current`, index, push, record. Nothing is built again for the same content, code and origin, and what the clock has made visible counts as content.
- **Scheduling.** The intake records the next scheduled time: the next moment a scheduled post goes out, by its moment, or by its triggers as far as what is scheduled tells, a post that waits for a scheduled one at that one's moment ([ADR 0076](0076-let-a-scheduled-post-wait-for-triggers-a-moment-or-another-posts-publishing.md), 2026-11-25). A timer, accurate to a second at the start of each minute, starts a run once that time has passed, and catches up on one passed during downtime. Lateness stays about a minute. A post that waits for another's publishing goes out in the build that publishes that one.
- **Live means that a release holding the post's latest version is current.** Recording comes after the release is current, so *live* never runs ahead of what visitors get.
- **Status per ID:**
  1. *failed*, with each refusal, when its version is the one refused;
  2. else *live*, when its version is the one the current release holds;
  3. else *failed*, with the build's reason, when the last build made no release and read that version;
  4. else *being published*, which is not stored but is the absence of a record.
- **Where the editor sees it:** a field in the post's form and a *Publishing* page listing every post, from the service. A scheduled post that waits for triggers shows each, in its rows, ticked where it has happened (ADR 0076). A failure says what could not be published, why, and whether visitors still see the earlier version. The words are made in one place. Refusals of menus and settings show there too, since they belong to no post.
- **A command the builder waits for has a time limit** (2026-11-26): the intake, the site's build and its search documents, each a program of its own. Every Node the builder starts loads the core's `src/node-exit.js` first, through `NODE_OPTIONS`' `--import`, which keeps V8's baseline compiler on its main thread, and which each Node passes on to the Nodes it starts in turn: npm, Astro and what they start. A command still running at the limit, `KONZILO_COMMAND_TIME_LIMIT`, ten minutes by default, is stopped with every process it started: it runs as the first of a process group of its own, which every process it starts joins and leaves only by its own doing, and the group is stopped by `SIGKILL`. A build whose intake or site's build is stopped runs once more from the start, the builder's log saying why, with what the stopped intake wrote undone, the content checkout put back to its last commit, and a confirmed deletion's code still confirmed. A build stopped again is recorded as failed, with its own reason, `failure.took-too-long`, "the build took too long and was stopped", which the publish status and the build's line show, and the release in use stays. The site's build clears its `dist/` before it runs, so pages a stopped build wrote, whole or not, are never published. A build that fails otherwise is not tried again. A search documents command that is stopped leaves the release live, and `unindexed`.
- **The build log** is one line of JSON per build, appended when it ends: `at`, `site`, `outcome` (`live` when every post is live, `failed` otherwise), `failures` as refusals, `unindexed` when the release is current but the search index was not updated, and `retried`, with the stopped command's words, when the build ran once more since a command of its first try took too long. A standing refusal is listed in every build's line until it is fixed, so a refused post still makes the builds heartbeat report 0.
- **A start prepares the site's code** in the builder's work folder: it copies the code from the site's folder as it now is, at every start, so that a change to a template is built from, and installs its dependencies only when what they are installed from has changed since the last install that ended. That is the site's `package.json`, its lock and its `.npmrc`, each as it is or as absent; for each package the site pins by a path, a tarball's bytes, such as a core's package in the site's `vendor/`, so that the record does not rest on the lock holding them, or what a folder's package ships, such as a core's checkout: its `package.json` and what its `files` names, or, where it names none, every file but its `node_modules` and what a dot hides; and the Node and the platform. What a checkout holds beside what its package ships, a test's or a build's output, starts no install, and a file it ships that cannot be read is named, and stops the start (2026-11-13). A start with nothing changed therefore runs no `npm` and needs no network. The record is one hash of all that, in the copy's `node_modules/.konzilo-installed-from`, removed before an install begins and written once it has ended, so that an install that fails or is stopped leaves none and the next start installs again, and it goes with the `node_modules` it speaks for. How an install treats the core depends on its pin ([ADR 0011](0011-pin-a-versioned-core-in-each-site-repository.md)): a core pinned by a checkout's path has no version to tell npm it has changed, so the installed copy and the lock are removed and npm resolves again; a core pinned by a tarball in the site's `vendor/`, a release's package named by its version, is installed from the lock, whose integrity holds its bytes. The live preview prepares its own copy the same way (ADR 0032).
- **The service's other timed duties** lie in ADR 0044.

## Why

- Editors need to know that their change is out, and why when it is not.
- Only the build knows when its release is current and why it failed.
- A request written during a build gives exactly one more build, since every build reads everything.
- JSON lines are plain: appended in one write, readable with `grep` or `jq`.
- Node 26.13.1, and Node 24 too, can stop for good as it exits by `process.exit()` (nodejs/node#67596), as Astro's command does after a build and the core's commands do once their output is taken. A build caught so had written its `dist/` and then stayed, using no CPU, and a builder that waited for it with no limit published nothing more until the container restarted, with no word of why. Keeping V8's baseline compiler on the main thread makes the deadlock rare; a worker of V8's next compiler can still wait the same way, so the time limit catches the rest ([ADR 0014](0014-test-at-two-seams-and-keep-the-acceptance-suite-small.md)).
- npm starts the build in a process of its own, and a Node waiting in its exit runs no handler of a signal, so only stopping the whole group outright stops the build.
- The deadlock comes by chance, so a second try nearly always gets through. Nothing shows that a `dist/` a stopped build wrote is whole, so a second try builds it anew rather than publishing it.
- A limit for each command says which of them stood still, and a large site's slow intake does not shorten the time its build is given.

## Considered and rejected

- **Stopping the command alone,** as `execFile()`'s own `timeout` does. npm would go, and the build it started would stay.
- **`SIGTERM` first, and `SIGKILL` after a while.** A Node waiting in its exit runs no handler, and nothing a stopped command was doing is used, so there is nothing to let it finish.
- **`--no-concurrent-sparkplug` in `NODE_OPTIONS`, or on the intake's command line.** `NODE_OPTIONS` refuses the flag, and a flag on a command line reaches that Node alone, not npm's build or what it starts.
- **Finding a command's processes by their parents.** A process whose parent has gone is another's child, and the process group is what the kernel keeps for this.
- **Publishing from a `dist/` a stopped build wrote.** Nothing shows that it is whole.
- **One limit for the whole build.** It would not say which command stood still, and a slow intake would shorten what the site's build is given.
- **More than one try, or a second try for any other failure** (Thomas, 2026-11-25). A build that fails otherwise fails the same way again.
- **Installing at every start.** Every start would need the network, and a quarter of a minute before the builder or the preview did anything.
- **The lock alone as the record.** It says nothing of a checkout's files under a path pin, and need not hold a tarball's bytes.
- **The record beside the copy, outside its `node_modules`.** It would outlive a `node_modules` that is gone.
- **A queue of build requests.** One more build covers every request.
- **Request times instead of versions.** Clocks would be compared between programs.
- **Recording when the intake ends.** A post would show live before visitors see it.
- **WordPress's cron, started by visitors.** It runs only while something loads it, so a scheduled post would be on time by accident.

## What practice has shown

- Save to public page took 19.7–21.2 s at 1,000 articles on 4 vCPU, and 4–5 s at 20 articles.
- A timer without one-second accuracy can make a scheduled post up to two minutes late.
- A version saved while a build ran must not be shown failed by a build that never read it.
- Pointing `current` back at an older release must record again.
- In Compose a save showed on the public page 6 seconds later, with the demo's 14 posts on a Mac, and the first build after a start took about 30 seconds.
- One builder, taking one request at a time, needs no lock: the steps run in that one loop. The hosting layer, which starts builds its own way, may need one.
- The ledger holds the source file's hash, so a post saved otherwise commits a new ledger with nothing new to show. What names a site's content for "nothing is built again" is therefore the content repository's tree without the ledger, which the site reads only for a feed's `guid`, the same as long as a post's file is.
- A site's code is named from what it was given and from the installed core, not from the folder it is built in, where a build leaves files of its own.
- V8's own trace of its baseline compiler, `--trace-baseline`, names the compiler's work on a thread of its own `[Concurrent Sparkplug]`, which a Node started by npm with `--import` of `src/node-exit.js` in its `NODE_OPTIONS` never wrote, nor an intake the builder started (`tests/build-commands.test.js`). V8 holds the name of the file it traces to in 128 bytes, so a longer path is cut and the trace goes elsewhere.
- Sveltia goes back to the list after a save, so an editor who stays there sees the status when opening the post again or on the *Publishing* page. A custom page is a `radio` in Sveltia's page switcher, and its heading is Sveltia's.
