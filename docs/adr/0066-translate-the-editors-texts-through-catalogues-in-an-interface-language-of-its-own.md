# ADR 0066: Translate the editor's texts through catalogues, in an interface language of its own

**Date:** 2026-11-10 · **Status:** Accepted. Settled by Thomas on 2026-11-10: every text the core ships is written in British English and translated through catalogues, Swedish first; the interface's language is chosen apart from the site's, the site setting a default and each editor choosing their own; what visitors read follows the content's language; a site's own label is one text for every language or a text per language. The mechanism is a technical choice; Thomas may veto.

## Decision

- **A catalogue per language,** `src/catalogues/<language>.json`: each text by a stable name, such as `form.title`, with named placeholders, such as `{menu}`. British English, `en`, is the source, and Swedish, `sv`, its first translation. `src/catalogues.js` reads them, for the intake, the build and the editor's code in the browser alike. A test fails when a catalogue lacks a text the source has, holds one the source does not, or names other placeholders.
- **The interface language** is, in this order: the editor's own choice, made through Sveltia's own language preference; else the site's `interfaceLanguage`, declared in the site description; else the site's main language, where the core has a catalogue for it; else British English. A choice the core has no catalogue for keeps Sveltia in that language and gives the core's texts in British English. The checker refuses an `interfaceLanguage` that names no catalogue.
- **Sveltia's own interface follows it.** For an editor who has chosen none, the editor sets Sveltia's preference to the site's interface language, with a mark of its own beside it, so that what Konzilo set is told apart from a choice. Where the browser's first language is the site's interface language, it leaves Sveltia's *Automatic*, which takes that language by itself, so that a first visit there needs no load more. *Automatic* is no choice, and so gives the site's. Sveltia reads its preference as it loads, before the configuration has said what the site's language is, so the editor sets it as the last load found it, and a load that finds it new to the browser, or changed, loads once more before Sveltia shows anything.
- **A generated configuration per interface language.** `konzilo-cms` writes `config.json` in the site's interface language, and beside it `config.<language>.json` in each language the interface comes in; `konzilo.language` names the one a file is in. The editor fetches the editor's choice, else `config.json`.
- **A language chosen while the editor is open** shows in Sveltia at once, and the editor then loads again, so that its own texts follow and one screen never holds two languages. It loads again only when Sveltia's preference has changed since it loaded, so that it never loads again by itself.
- **A site's own label,** a type's or a taxonomy's `label` and `plural`, a menu's, a setting's, a field's, a presentation's and its options', and a component's and its attributes', is one text for every language, or a text by interface language with British English required: `{ "en": "Article", "sv": "Artikel" }`. The editor shows it in the interface language. Where a visitor reads it, in a feed's title, a search document or `post_type.labels.singular` in a template, it is the page's language's, else British English's; a refusal carries it as given, and names it in the language it is shown in, its first letter lowered in the middle of a phrase but in an abbreviation, such as FAQ. A form's label and its fields' are read by visitors, so each stays one text.
- **The editor's own code in the browser,** the body field, the image field, the structure field, the preview in its pane and in its window of its own, the publish status and the article parts' fields, takes the interface language from the configuration it fetched, `konzilo.language`, before it draws anything, and never the browser's. It names each text whole, `body.loading`, by its area: `body`, `image`, `structure`, `preview`, `publishing` and `parts`. A test holds each name its code asks for against the source, since a name the source lacks would stop the editor, and each text of those areas against its code. A moment it writes, a scheduled post's among them, is in the interface language too.
- **The settings groups' texts are the catalogues',** each by a name made from where `settings-groups.json` declares it: a group's `settings.<group>.label` and `settings.<group>.description`; a setting's `settings.<group>.<setting>.label`, and its `….help` where the catalogues have one; a part's `settings.<group>.<part>.label`, its `….description` where they have one, and its settings' below it; the part per post type's settings' below `settings.<group>.types`; and a select's options' `….options.<option>`, the option's value in lower camelCase, `theSummary` for `The summary`. The declaration holds no text an editor reads: the checker refuses one written there, and a setting whose label the catalogues lack, naming the text. The editor shows them in the interface language, while an option's value stays what the settings file holds. A setting's default that visitors read, such as a consent text, is content, and stays in the content's language.
- **What visitors read** of the core's own is in the catalogues too, by names under `site.`: search's, a form's, the text of a post list that matches nothing, the pager's, the breadcrumbs', the lightbox's, the language switcher's label, an embed's sentence that the site's script has not run, the plain text of a page not found, the consent's own words and the facts of the core's services. It takes the content's language, the page's on a site in several, and never the interface language, so that a Swedish site's pages are in Swedish whatever language its editors work in. A language without a catalogue takes British English, and the build warns of it, as before. A setting's default that visitors read, such as a consent text, names its text, `{ "text": "site.settings.consent.bannerTitle" }` in `settings-groups.json`, and so does a core service's purpose in `services.json` and `tag-managers.json`; each of a site's languages takes the text in its own, the editor's field for it among them.
- **The consent's own words reach `src/consent/` with its input,** as `catalogues`, the catalogues by language as `src/catalogues/` holds them, since the folder imports nothing outside itself, so that another site can copy it. Konzilo's build hands in its own. The folder takes the page's language's catalogue, else British English's, and formats dates, times, numbers and countries in `en-GB` for British English, `sv-SE` for Swedish and the language itself for another catalogue, unless the caller gives its own. The defaults of the texts of the right to object, which it falls back on, are the consent settings' own, by the same names.
- **A refusal or a warning by name.** The intake gives each with its reason by its name in the catalogues, `refusal.…` or `warning.…`, and the values that fill it; a build that made no release says why by a name too, `failure.…`. A value is given as it is, as a text by name of its own, such as an element's, `body.element.heading`, as a site's own label, `{ "label": … }`, or as a list joined by *and* or *or*. The editor shows each in its interface language, at Save, in the preview and in the publish status, with the block, the field, the entry or the setting it names, through `src/refusals.js`, which imports only the catalogues. Each also carries its reason and its message in British English, which the intake's command line and the build log write, so that what an operator reads does not depend on a customer's choice. The rule data holds no words: where it refuses in words of its own, an element's setting or an embed, it names them, `{ "name": "refusal.list-number" }`, and a settings group's form names its refusal the same way. Words a site gives, its components' own check and an attribute's `refusal`, have no name and are shown as given.
- **The catalogues come in beside the two-language tables** read through `src/texts.js`, which keep working until their texts have moved to the catalogues, area by area, and then go. The form's labels in the generated configuration move first.

## Why

- A consultant who reads no Swedish must be able to work on a Swedish site, and a Swedish editor must not meet one screen in two languages.
- A language is added by translating one file. A table of two languages in code grows with each language.
- A name made from where a setting is declared cannot drift from it, so a new setting needs nothing but its texts in each catalogue.
- A refusal carried in words could be shown in one language only, and the editor, the command line and the build log each need another. Carried by name and values, each shows it in its own, and a test holds that every name the intake gives has its words in every catalogue.
- Sveltia's preference is where an editor already looks for a language, and Sveltia keeps it in the browser.
- A configuration per language is plain Sveltia configuration, generated and tested whole, and leaves the choice to the browser alone.
- What visitors read is content, so it follows the content, as a post's own text does, and a language is one file to translate for editors and visitors alike, the consent's words included.

## Considered and rejected

- **The browser's language,** as Sveltia and the body field followed it. It is neither the site's choice nor the editor's, and one form mixed it with the site's.
- **One configuration whose labels the browser translates.** Sveltia would be handed a shape of Konzilo's own, and the labels would leave the configuration that is generated and tested.
- **A name of its own for each settings text, written beside the setting.** It would say again where the setting is, and could be left behind when a setting moved.
- **Importing Sveltia once the configuration has been fetched,** which would need no load more: in WebKit it broke Sveltia's own image code (below).
- **Languages with a region, `en-GB` or `sv-SE`, in the site description.** The interface comes in a language, and its catalogue's name says which; `en` is British English.
- **What visitors read in the interface language.** A visitor would meet the language an editor chose.
- **A catalogue of the consent's own inside `src/consent/`,** which the folder could import. A language would then be two files to translate.
- **`src/consent/` importing `src/catalogues.js`.** Another site could no longer copy the folder alone.
- **A refusal in the interface language, written so by the intake.** The intake runs once for every editor, and the build log is read by an operator, so neither can know whose language to write.
- **The refusal's words in the rule data, beside the catalogues.** British English would then have two sources, and the rule data and a catalogue could drift apart.

## What practice has shown

Sveltia 0.256.1:

- Sveltia reads its preferences as it loads, from `sveltia-cms.prefs` in the browser's storage, `locale` among them, `auto` until a person chooses.
- Imported later than the editor, as a part of its own once the configuration had been fetched, Sveltia threw "Cannot load blob:… due to access control checks" in WebKit, twice after each sign-in, from its own image code. Imported with the editor, as before, it does not; hence the preference as the last load found it, and the one load more.
- Sveltia takes a preference of `en` as `auto`, so British English is set as `en-GB`.
- Sveltia sets `lang` on the page's root element when its language changes, which is what the editor watches for a choice.
- Where the language Sveltia shows is not the browser's, Sveltia offers the browser's in a bar at the top, in that language: "Sveltia CMS is now available in English (US)! Change Language Later". It comes once per browser and repository, until a person answers it; *Change Language* is a choice like any other.

## Consequences

- The web image copies `src/catalogues.js`, `src/catalogues/` and `src/refusals.js`, which the editor imports.
- The body field's, the preview's and the publish status's texts are in the catalogues, read through `src/cms/body/texts.js`, so one screen of the editor is in one language. The preview's window of its own needs no language of its own, since the editor draws it.
- The settings groups' headings, labels, help and options' labels have moved to the catalogues, under `settings.`, in British English and Swedish.
- The rest of the core's texts move to the catalogues: the body field's, the preview's, the publish status's and what visitors read, from the two-language tables, and the settings groups', in English alone so far. This record says when the tables are gone.
- What visitors read has left the two-language tables. The package exports the catalogues, `@kntnt/konzilo/catalogues/<language>.json`, for a site that renders the consent with the package's functions, and the site template's 404 page shows the core's plain text of a page not found, `pageTexts().notFound`, which a site may give its own of in `konzilo({ texts })`.
- Refusals and warnings, the build's reasons for making no release among them, carry a name and values. `tests/intake-refusals.test.js` has a case for each name of `refusal.` and `warning.` in the catalogues, which gives it, carries it as JSON and shows it in each catalogue's words. Not yet by name, and so in British English in every language: the grammar of a redirect pattern and the shape of a rule's target (`src/format/patterns.js`, `targetProblem()` in `src/format/redirects.js`), and the problems of a service an Admin declares in `services.json` (`src/format/declared-services.js`), files an Admin writes by hand. The site description's checker is a developer's, in British English alone.
