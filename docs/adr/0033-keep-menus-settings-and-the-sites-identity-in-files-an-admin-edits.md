# ADR 0033: Keep menus, settings and the site's identity in files an Admin edits

**Date:** 2026-11-02, amended 2026-11-10, 2026-11-11, 2026-11-12 and 2026-11-13 · **Status:** Accepted. Settled by Thomas: the Admin changes menus and site settings, and the start page's layout stays in the site repository until page composition (2026-10-27); the logo and icon are uploaded in the editing tool as image fields (2026-11-02); an Admin who opens the settings sees each setting's default where the file holds none, and a save that leaves a setting untouched leaves the site as it was, with no new patch of Sveltia's code (2026-11-11); an Admin chooses a page as the start page, as the page for addresses not found is chosen (2026-11-13). The rest is a technical choice; Thomas may veto, among them the core's field for a setting with a default, which shows the default and keeps no value where the default is chosen again (2026-11-11), a menu entry's description, one line of plain text of at most 160 characters, which the intake refuses otherwise rather than cleans (2026-11-12), and how the chosen page is the start page (2026-11-13): the setting `startPage.page`, chosen among the site's pages as the 404 page is; the chosen post's file as its type writes it, at the content folder's root, `start.<type>.md`, which the site reads as a post of its type at `/` alone; a choice that cannot serve, or that is the page for addresses not found, leaving the site its own start page with a warning; and a site in several languages offered none ([ADR 0042](0042-publish-a-site-in-several-languages-with-a-prefix-per-language.md)).

## Decision

- **The site description declares both:** `menus`, each named in lowercase letters, digits and hyphens with a `label`; and `settings`, each in the form of a field of the site's own.
- **The core declares settings groups of its own,** the same on every site, in one data file, `settings-groups.json`: settings with defaults, optionally a part per post type (`types`), a condition on the description (`when`) and a form of its own. A group's label and description, and its settings' labels and help, are the catalogues', in the interface language (ADR 0066). A group's name is reserved. Secrets and addresses, such as recipients lists and retention, are kept by the service, never in Git.
- **Admins edit them as file collections in Sveltia,** with the groups after the site's own settings, a label per section and each default shown.
- **A setting with a default is the core's field for a setting** (`konzilo-setting`, `src/cms/settings/`), which draws Sveltia's own field for it, a switch, a number, a choice or a text, through `CMS.getFieldType`. It shows the default while the settings file holds no value, and keeps no value, which a save leaves out of the file, where the default is chosen again or the field emptied. Sveltia is given no default of its own for any setting, so it writes none into the file. A number or a text being typed shows what is typed, and a value set from Sveltia's menu of the field shows as it is, with the default where it is none.
- **The source holds values, the published side says what the site does.** Only values that differ from a default are kept in source, so a default the core changes reaches a site that never changed the setting. The intake writes `settings.json` with every setting, typed, each with its value or default, a yes-or-no always, a day as `"YYYY-MM-DD"`, a choice of a post as its title and current address, and an image as its master. In two spaces with one final newline.
- **The start page an Admin chooses,** in the group `startPage`, is one published post of a type with an address, by ID, chosen among the site's pages as the page for addresses not found is ([ADR 0040](0040-answer-unknown-addresses-with-a-chosen-page-and-count-them-without-the-visitor.md)). The intake writes the post's file as its type writes it, at the content folder's root, `start.<type>.md`, and leaves the choice out of `settings.json`, which the site reads as a post of its type, its entry's ID `/`, which no slug or path is, at the start page's address and at no other ([ADR 0034](0034-answer-each-public-address-from-one-holder-in-a-fixed-order.md)). `startPages()` gives a site's start route the chosen page, which it draws through `Body`, or none, where it draws a start page of its own. A chosen post that cannot serve, not published, missing or of a type without an address, or that is the page for addresses not found, which has no address, leaves the site its own start page, and the settings page warns; a refused one keeps the file it was last published with, as any refused post does. A site in several languages is offered none, and one a settings file holds there is left out with a warning ([ADR 0042](0042-publish-a-site-in-several-languages-with-a-prefix-per-language.md)). What its old addresses, its breadcrumbs, its head, the sitemap, its Markdown alternate, search and the live preview say of it, ADRs 0036, 0037, 0046, 0047, 0053 and 0032 say.
- **Menus are written** as `menus/<menu>.json`: `{ "items": [ { "title", "url", "description", "items" } ] }`; `{ "items": [] }` for a place without a menu; an entry with no address has no `url`. An entry for a post leads to the post's current address, by ID, labelled with the post's title unless it has its own.
- **An entry's description** is a line under it, which a large menu shows, optional at every depth: one line of plain text, trimmed, of at most 160 characters as Sveltia counts them, its code points after the trim, and kept only when it holds any. The form's field is one line with that most (`maxlength`), and the intake refuses the menu whole for a description with a line break, with HTML, longer, or not a text. `siteMenu()` gives it to a template as `description`; an entry without one has none.
- **An entry whose post has no page now is left out, with the entries under it, and the build warns.** It comes back by itself. **A menu or the settings the site cannot publish are refused whole,** naming each entry by its place (`2.1`) or each setting by its path (`search.types.post.title`), and keep their last published file.
- **The site's identity:** `title`, `logo` (`{"src":"media/<name>","alt":"…"}`) and `icon` (`{"src":"media/<name>"}`) are written before the declared settings, each only when set; the masters are `logo-<hash>` and `site-icon-<hash>`. A logo's alt text is a field beside it. A purge keeps what the logo and icon use.
- **Icons.** The icon must be square, and a raster one at least 512 px. Every build makes, at the site's root: `favicon.ico` (16, 32 and 48 px), `icon.svg` where the icon is one, `apple-touch-icon.png` (180 px, opaque), `icon-192.png`, `icon-512.png` and `site.webmanifest`. `Head` links them. A site's own file at one of these addresses fails the build. The theme colours come from the design's values: `primary` and `base`.
- **Astro reads them as collections,** `menus` and `settings`.

## Why

- Customers change what is theirs without asking Kntnt.
- A setting shown otherwise than the site has it misleads the Admin: a switch shown off that is on by default is switched on on purpose, or left as it seems. A default the form wrote into the file at a save would stay there when the core changes the default. Sveltia does both (below), and its field cannot be told otherwise without a patch, so the core's field draws Sveltia's with the value the site has.
- Writing defaults into the file means the content files say exactly what the site does.
- A visitor never meets an entry that leads nowhere.
- A description is read under an entry, in a column of a large menu, where a sentence or two fits and a paragraph does not; 160 characters is about two short lines there. Refusing what does not fit, rather than cutting or joining it, leaves the Admin's words as the Admin wrote them, as a term's description, which holds no HTML either.
- Refusing a menu whole keeps the menu visitors see one the Admin made.
- An editor writes the page a visitor meets first, of the site's components, as any page (Thomas, 2026-11-13). The post's file as its type writes it lets every part of the site read it as a post of its type: its frame, a canvas's without header and footer, its body, its search and sharing fields, its dates and its place in lists are a post's. At the root, named by its type, it moves when the choice does, so that the site, its dev server and the deletion guard see the change as they see a post that moves.

## Considered and rejected

- **A page, option and file per feature.** Many screens and many refusal paths.
- **Each site declaring the core's settings.** Every site would repeat them.
- **The settings file read through a format of the editor's own that fills in each default, and written back without them.** Sveltia's draft would hold every default, so each group's closed bar would open by itself as one that holds something (ADR 0029), and the settings page would show every group open.
- **A field's default in Sveltia's configuration alone.** It shows the default only where the file holds the setting's group, and writes it into the file at the next save.
- **A patch of Sveltia's object or switch.** No new patch of Sveltia's code (Thomas, 2026-11-11).
- **A description cleaned by the intake,** its HTML taken out, its lines joined or its end cut. The site would show words the Admin never wrote, and the form, a line with its most, already keeps an Admin from most of it.
- **A description in Markdown or with links.** An entry that leads somewhere is a link itself, and a link within its line would be one inside another.
- **An entry for a post with no page as its text alone.** In a menu, a label that leads nowhere is a broken menu.
- **Keeping the entries under a left-out entry in its place.** The menu would take a shape the Admin never gave it.
- **The start page's file as the 404 page's, its title and body alone, in a collection of its own.** The site could not tell a canvas, which has no header or footer, from a page, and would lose the post's search and sharing fields, its dates and its name in breadcrumbs.
- **The chosen post's file kept in its collection's folder, with a key in its frontmatter that makes it the start page.** The key would be a name no field of a site's own could have, which would refuse a site description that has one so named, and every part that tells a post's address would have to read the post's data, not its file. A change of choice would not move the file either, so that a dev server would not see it.
- **The choice among every type with an address.** Sveltia's relation chooses in one collection, and the page for addresses not found is chosen among the pages.

## What practice has shown

Sveltia 0.256.1, where the settings file lacks a setting of a core group:

- Where it lacks the whole group, Sveltia holds the group as nothing, gives its fields no default, and shows a switch off and a number empty, *Freshness* and *Half-life in days* of *Related posts* and AI visibility's *Markdown* among them. A save after another change, such as the site's title, wrote nothing of the group, so the site stayed as it was. A setting written in the group was lost at that save, the group written as `null`, as in every closed bar whose object a file lacks, which the closed bar's patch takes away once something is written in it ([ADR 0029](0029-configure-sveltia-from-the-description-and-patch-its-npm-build.md)).
- Where it holds the group but not the setting, Sveltia fills the field's default into the form, and a save writes it into the file.
- Save stays off until a value changes. A switch of a group the file lacks, switched off and on again, holds no value but is a change to Sveltia, and its save leaves the file as it was.

## Consequences

- An Admin cannot keep a setting with a default empty; a feature that needs "none" offers it as a value.
- An Admin who chooses a setting's default again, or empties its field, leaves the file without it, so the default the core then has applies.
- `tests/intake-site.test.js` holds an entry's description written and refused, on a site in one language and in two, `tests/intake-golden.test.js` the examples of `content-format.md` as source files and back, `tests/cms-config.test.js` the field at every depth, and `tests/site-template.test.js` what `siteMenu()` gives a template, in one language and in two.
- `tests/cms-config.test.js` holds which settings are the core's field and that no setting has a default of Sveltia's, `tests/cms-settings.test.js` what the field shows and keeps, and `acceptance/form.test.js` (`a setting's default in Sveltia`) the defaults shown, a closed bar left closed, a save after settings changed and changed back that leaves the file as it was, and a save that keeps only what differs from a default, and (`a value written in a closed bar whose object the file lacks`) a setting written in groups the file lacks, one within another, kept, in Chromium and Firefox, whose private file system the test repository keeps its files in.
- Fields of a group may take a regular expression of the whole value with the words of its refusal, which `preSave` and the intake both check.
- A group may be offered `unless` a path of the site description leads to a value, as the start page's group is unless the site declares `languages`.
- The editor offers the start page among the site's pages alone, so an Admin chooses a canvas or an article only in the settings file's source.
- `tests/intake-site.test.js` (`the start page an Admin chooses`) holds the chosen post's file, its address, its old address and its children's, a refused one, a showing other address, a rule that leads to it, the choices that cannot serve and the ledger, `tests/intake-command.test.js` its file moved and counted by the guard, `tests/cms-config.test.js` the setting in one language and none in two, and `tests/site-template.test.js` the chosen page at `/`, a canvas with its list's later pages, an article in its feed and the site's own start page again.
