# ADR 0053: Search with Typesense, indexed from the published files

**Date:** 2026-10-29, amended 2026-11-11, 2026-11-12 and 2026-11-13 · **Status:** Accepted, Typesense settled by Thomas on 2026-10-29. The rest is a technical choice; Thomas may veto, among them the start page an Admin chose in the index at `/`, and a post's slugs holding those of its terms' ancestors, so that a search within a term finds what its page lists (2026-11-13); and a taxonomy's parameter on the search page as its own name with its terms' slugs, and the status's words (2026-11-12), "3 results for “lantern” in Rivers or Lakes and in News", "12 results in Rivers", in Swedish "3 träffar för ”lykta” inom Floder eller Sjöar och inom Nyheter", "12 träffar inom Floder".

## Decision

- **The index.** Each site has a collection, an alias named as the site, and a key that only searches it. Every build makes the site's documents from its content files once `current` is switched, imports them into a new collection and switches in one step. A failed indexing leaves the release live, is said in the build's line, `unindexed`, and alerts in office hours.
- **The documents and the schema** come from one function of the npm package, which reads the content files as the site does. A type takes part unless it says `"search": false`. Each taxonomy's terms are in a document twice: by their names, `terms_<taxonomy>`, which a query is matched against, and by their slugs, `slugs_<taxonomy>`, which a search is filtered by and a query never matched against, one field in every language, since a term's slug is the same in each. The slugs are of a post's own terms and of every term above them, each once, as the terms' files and their `parent` give them, so that a search within a term finds the posts of the terms below it too, as the term's page lists them ([ADR 0039](0039-write-a-post-list-as-a-directive-evaluated-at-every-build.md)), while the names are of its own terms alone, which a query is matched against. A post marked `noindex` has no document. The start page an Admin chose ([ADR 0033](0033-keep-menus-settings-and-the-sites-identity-in-files-an-admin-edits.md)) is a document of its type at `/`, its id its file's path, `start.page`, so that a visitor finds its words as any page's. Typesense stems a field in the language its `locale` names; a language it has no stemmer for is tokenised unstemmed. Infix search is on the title and the body alone, since it costs memory.
- **The route.** `GET /_konzilo/search` takes `q`, `page` and `filter_by` alone, drops every header of the visitor's, and adds a scoped key made from the site's search key, which holds the search every query runs, the fields and their weights, infix, typos, a page of ten results, so that a visitor's query can change none of them. No page holds a key. It answers `405`, `404` and, while Typesense does not answer, `502` with a message.
- **The search page** is a page of the site's design at the address `search` declares; its script asks the route and shows the results. It narrows by a type, `type`, and by terms, as a list's filter sends them: each taxonomy whose terms are in the documents by its name, `category`, `topics`, `authors` or a site's own, repeated for each of its terms by its slug, `?topics=rivers&topics=lakes`; one taxonomy's terms joined by or and the taxonomies by and, in `filter_by` on the slugs; and with terms and no words, every post of them, `q=*`. A taxonomy named `q`, `page` or `type`, the page's own parameters, does not narrow it. Its form keeps the type and the terms in hidden fields and its links to other pages in their parameters, and its status names the terms in the page's language, the page holding each taxonomy's terms' names by their slugs. It has no class or element of its own for them, so a design styles them with the classes the page has. In a preview it says that search is not there. A type whose own folder holds that address is refused; one at the root leaves it to its posts.
- **Per language,** one index, each document with its language; each language's texts in fields of their own with that language's analysis, `title_sv`; each language's search page after its prefix, through `filter_by`.
- **Locally,** Compose runs the same Typesense, in a network of its own that only the web server shares, with no port and no way out (ADR 0005). The seed makes its admin key and the site's search key once, and Typesense reads its admin key from a configuration file, never the environment. The builder indexes at each switch of `current` and at its first build after a start, which keeps no word of an index made before, with the documents that `konzilo-search documents` makes in the site's own dependencies, as a program of its own, since the builder's image has no Astro to read content files with; and it writes the route for the web server, with the scoped key, in a volume of its own, outside every release, to Typesense at the peer address the builder indexes at, `http://typesense:8108` in Compose, which another arrangement names by `KONZILO_PEER_TYPESENSE` ([ADR 0002](0002-let-the-core-know-one-site-and-run-it-everywhere-with-docker-compose.md)); on a site without search, a route that says there is none. The web server answers the route as the dev server does: it passes on each of `q`, `page` and `filter_by` as decoded and encoded again in Typesense's address, `page` 1 where none is given, and leaves out every other parameter; a value given twice comes as the two joined by a comma.

## Why

- Only Typesense's infix search finds a word inside a Swedish compound.
- An index made from the published files never holds a draft and needs no backup.

- A list's filter sends what the search page takes, so a search from a list searches within what the visitor ticked; the slug, not the name, since a name can change and differ by language while the slug of a term's file is the same in each.
- The status says what was searched within, in words, since a visitor who came from a list's filter sees no ticked boxes on the search page.

## Considered and rejected

- **Pagefind,** which has no infix matching.
- **Keys in the browser.**
- **Indexing scraped HTML.**
- **A parameter of its own for the terms,** such as `terms=topics:rivers`, or the filter's own syntax in the address: a list's filter would have to write it, and an HTML form cannot.
- **Filtering on the names,** `terms_<taxonomy>`, which change with the language and when an editor renames a term.
- **Classes for the chosen terms on the search page,** which every design would have to style; the status says it.

## What practice has shown

- A known limit: the search page writes the name of every term of each taxonomy it narrows by into its `data-taxonomies`, so that its status names the terms it searched within without asking anything more. The page grows with the number of terms, by about the length of a term's slug and name for each, which a taxonomy of thousands of terms will feel in every load of the search page.
