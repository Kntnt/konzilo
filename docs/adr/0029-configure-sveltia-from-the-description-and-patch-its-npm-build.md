# ADR 0029: Configure Sveltia from the description, and patch its npm build

**Date:** 2026-11-03, amended 2026-11-10, 2026-11-11, 2026-11-12, 2026-11-23 and 2026-11-25 · **Status:** Accepted as a technical choice, within Thomas's decision of Sveltia (ADR 0001); Thomas may veto, among them, on 2026-11-11: a closed bar takes away the `null` Sveltia holds for an object the file lacks once something is written in it, in the closed bar's own patch, rather than Sveltia's writer of the file leaving that `null` out at Save; and on 2026-11-25: the sign-in window opens empty and is sent to Forgejo by the editor that opened it, by a patch, rather than the editor starting in that window with its icons left unmade there, or the console check letting pass what WebKit refuses a page that is leaving.

## Decision

- **Configuration is generated, never committed.** `konzilo-cms` makes it from `site-description.json` and the settings groups at deploy and on a local start, once in each interface language, with labels in that language (ADR 0066). Nothing is stored that could drift.
- **Fields map plainly.** Text, number, toggle, date and select controls take Sveltia's own fields. A taxonomy or a parent is a relation by ID. A featured image is an object of image and alt text. Search and sharing is one object of three parts, each with its fields, which is how a source file holds them too: `seo: { search, sharing, advanced }`, where a content file has one flat map. A relation offers no new entry from inside the form, but for a post's terms: under a parent it would make the new page the parent of the page in hand. Settings groups and menus are file collections with nested lists, and a setting with a default is the core's field for a setting, which draws Sveltia's with the default where the file holds none ([ADR 0033](0033-keep-menus-settings-and-the-sites-identity-in-files-an-admin-edits.md)). Empty optional fields are left out, since the schemas refuse an empty string.
- **The build.** Sveltia's npm build (`npm/index.js`, not `dist/`, which holds unpkg addresses) at an exact pin, inside the core's package. It carries a data-file patch for each fault found, each failing loudly if its anchor moves. Sveltia's shared code and its Forgejo backend are chunks of their own beside it, `npm/chunks/init-*` and `npm/chunks/gitea-*`, whose names change with each release; a patch names the chunk that holds what it patches, and three globals set there hand the main script what it no longer holds: Sveltia's reading of a file, the kind of error whose words Sveltia shows as they are, and the backend's reading of a file at a commit.
- **The patches needed:** Forgejo's OAuth scopes, which Sveltia joins with commas; a retry when two people save at once, after the check against the latest save made anew; the lock of a form ([ADR 0073](0073-lock-a-form-to-the-tab-that-has-it-open-and-refuse-a-save-older-than-the-latest.md)): Sveltia's read-only state following it, the line above a read-only form, the mark of a held entry in the list, a deletion that needs the lock, *Save Anyway* gone, its warning and refusal in the core's words with a Reload that keeps the Editor's changes as a draft backup, and a backup older than the entry's latest save shown read-only and never offered to be saved; a form's revisions ([ADR 0074](0074-show-a-forms-revisions-from-the-source-history-compare-any-two-and-restore-one-into-the-form.md)): the core's list in place of Sveltia's history panel, Sveltia's reading of a file, its restore of a draft backup and its check of unsaved changes handed to the core, and a button in the refusal of a stale save that compares the latest save with the form; the wording above a `preSave` refusal, which the field gives by a global the patched dialog asks; the "now available on mobile" banner; Sveltia's Swedish *Återställ standard*, which says *Återställ standardvärde* as the core's groups do, so that one act has one word (Thomas, 2026-11-24); a relation's `allow_add: false`; a relation's *Edit* of an existing entry it names, which Sveltia saves along with the form under no lock of the entry's own, while an entry added from the form may still be edited there; an object's `accordion: true`; the preview pane as a `srcdoc` document in place of a blob, since WebKit refuses a blob under the editor's `frame-ancestors` and sends no cookie to a frame inside one (ADR 0032); and the sign-in window, which opens empty and is sent to Forgejo's page by the editor that opened it, where Sveltia opens it on the editor's own address and has the editor, once started there, send it on, since WebKit refuses whatever a page asks for once it has started for another. The same file patches what the field brings: a list item's selection (ADR 0030), a table cell's click (ADR 0021) and the runtime's probe of `new Function` (ADR 0016).
- **Backend.** The `forgejo` backend with PKCE only (`auth_methods`), no token sign-in, and the Simple Workflow.
- **Sveltia lives on the admin host,** `<site>.konzilo.app`, as static files, with a Content Security Policy of its own and without a cross-origin opener policy, since its sign-in uses a popup. That host never shows editor-written HTML.
- **What an editor rarely needs is a closed bar.** Search and sharing and the settings groups are accordions: a bar with its label, closed, with no box to tick and no star, holding nothing until something is written in it. One that holds something opens by itself, since a closed bar must not hide that a post is kept out of search engines. A long hint waits until its bar is open. Sveltia holds an object the file lacks as `null`, which wins over what is written under it at Save, and its box to tick takes the `null` away as it adds the object; a closed bar takes it away once something is written in it, and adds nothing else, so a bar opened and left adds nothing to the file. Sveltia has none of this, so it is a patch for the option `accordion: true`, and `form.css`.
- **A post's form is in field groups** ([ADR 0071](0071-draw-a-posts-form-in-field-groups-each-with-one-menu-and-keep-the-source-flat.md)), each one field of Sveltia's with one menu, the core's own or an object's. A closed bar of a post's teaser, search, sharing or structured data shows its menu at its end, over all it holds. A post's file is read and written through a format of the editor's own, under Sveltia's names for YAML front matter, `yaml-frontmatter` for the built-in types and `frontmatter` for a type of the site's own, which keeps its fields flat; with no new patch.
- **`preSave` refuses.** A handler sends the draft to the service's check, and throwing stops the save with the reason. An address another post holds, a required field left empty, or a change only an Admin may make is stopped at that moment, naming where it is. The intake remains the check that counts.
- **Pages in Sveltia,** through `CMS.registerCustomPage`: Publishing, Submissions, Mail, with each form's recipients list and retention, Personal data, with a person's submissions, Consent records, Policy violations, Addresses not found, Redirects with CSV, Privacy texts and Users. Everything else an Admin edits is plain forms. A custom page gets no props, so it reads the user's token from Sveltia's storage (`sveltia-cms.user`), which is undocumented, and is pinned and tested at each raise.

## Why

- A description that drives every reader cannot disagree with itself.
- A file left to be regenerated by hand would drift, so nothing is left.

## Considered and rejected

- **Sveltia's Editorial Workflow.** It is a review step, which Thomas has settled against (ADR 0008).
- **A committed configuration file per site.** It would be a second definition.
- **A `null` with something written under it left out at Save, in Sveltia's writer of the file.** The live preview reads the entry Sveltia builds from its draft, where the `null` wins too, so it would still not show what is written in the bar; and the draft is where Sveltia's own box to tick takes the `null` away.
- **The editor started in the sign-in window, with its icons left unmade there.** The two reads WebKit refused were of the icons, but they are only what the editor happened to be doing as the window left: anything else it starts there in those milliseconds, now or after a raise of Sveltia, is refused in the same way, and the editor is loaded once more at every sign-in for nothing but to send the window on.
- **Letting what WebKit refuses a leaving page pass the console check,** as Firefox's stopped fonts of a closing window do. The check would then say nothing of a load refused for another reason in that window.

## What practice has shown

Sveltia 0.256.1:

- The comma-joined scopes reach notifications and organisations (200), the patched ones do not (403). This holds on Forgejo 17.
- A refusal from `preSave` shows "There was an error while saving the entry. Please try again later." above Konzilo's reason, which is wrong for a refusal. The patched dialog takes the field's words where the reason is the field's, and any other failure keeps Sveltia's. The title stays "Error". Sveltia also logs the refusal with `console.error`.
- `preSave` runs after the entry is built from the draft, too late for a field to write what it holds back, so the body field writes within 50 ms of a key, on blur, and on Mod-S before Sveltia reads the draft.
- An optional object the file lacks is `null` in Sveltia's draft, a new entry's and a read one's alike, and stays so beside what is written under it where no box was ticked. At Save Sveltia keeps an empty object whose fields hold something, and its `unflatten` lets the `null` win over them, so a value written in a closed bar was lost without a word: a new page's or an existing page's title tag under *Search* as `search: null`, and a half-life written in a settings file without *Related posts* as `"related": null`. Sveltia's memory of the saved entry still showed the value; the file read back did not. `acceptance/form.test.js` (`a value written in a closed bar whose object the file lacks`) reads the file back after a save, for settings groups, one within another, a new page with a title tag and a structured data type, and an existing page, in Chromium and Firefox, whose private file system the test repository keeps its files in.
- `registerFieldType` starts loading React, ReactDOM and Immutable at once, not when an entry opens, 285 KB (86 KB compressed) in chunks of their own, so they come after the first paint on every load.
- **Two people saving different entries at once:** in 2 of 6 rounds one got the error dialog, with "PushRejected Error: … cannot lock ref 'refs/heads/main'" as the reason. Through REST, 3 of 4 parallel saves got 403. Saving again worked, and the draft stayed in the form. A commit takes about 0.5 s, so it is rare on a small site. The save is now tried again by itself ([ADR 0073](0073-lock-a-form-to-the-tab-that-has-it-open-and-refuse-a-save-older-than-the-latest.md)), and `acceptance/lock.test.js` saves two entries at one moment in each engine.
- **Two people, one entry:** Sveltia warns the second person while editing and at Save, with *Save Anyway* or *Cancel*. *Save Anyway* overwrites the other person's change, which then stays only in Git's history; the warning comes also when they changed different fields. A stale `sha` alone gets 409 from Forgejo, so an old copy cannot overwrite by accident. *Save Anyway* is now gone, and the form is locked to one tab ([ADR 0073](0073-lock-a-form-to-the-tab-that-has-it-open-and-refuse-a-save-older-than-the-latest.md)).
- Sveltia keeps a draft backup with the entry it was made from, `baseEntry`, and restoring one made before a later save gives the form that older entry back, so that its save meets Sveltia's own warning of a later save. A form of a read-only collection is read-only through one function, which the editor's line, its Save, its Delete, its backups and each of Sveltia's fields ask.
- Sveltia follows the browser's language until a person chooses one in its preferences, so it read "Logga in med Forgejo" and "Post sparad." in a Swedish browser, while collection and field names come from the configuration. So the editor sets that preference to the interface language (ADR 0066).
- A custom field's props are `value`, `field`, `forID`, `classNameWrapper`, `entry`, `getAsset`, `onChange`, `addFile` and `pickFile`. It cannot list other entries; a preview template gets `getCollection`. React is `window.__SVELTIA_CMS_REACT__`. Set `window.CMS_MANUAL_INIT = true` before loading the build, then `CMS.init({ config })` with `load_config_file: false`.

Sveltia 0.271.2:

- The npm build keeps the code its backends share in a chunk, `init-*`, and each backend's in one of its own, Forgejo's in `gitea-*`, read when it is used. The main script imports what it needs of them under names of its own, and what it does not import, such as the reading of a file, is out of its reach. The editor's bundle evaluates those chunks before any code of the module that imports them, so Sveltia read its preferences before the editor had set them, and closed a saved entry; the modules it reads as it loads, the flag that stops it starting by itself, the preferences and the interface language, are therefore a chunk of their own, `before-sveltia`, which the editor imports first (`scripts/build-editor.js`).
- A relation offers *Edit* for an entry it names, from 0.257.0, which opens the entry in a dialog and saves it in the same commit as the form, refused where the entry was saved meanwhile but under no lock of its own: another tab could hold that entry's form. The patch keeps it to an entry added from the form, which exists nowhere else yet.
- The dialog that offers a draft backup leaves the form in view, from 0.266.0, read-only until the Editor answers. Sveltia's read-only check of a form covers that wait too, and its check of a collection, which the line above a read-only form now follows, is the one the lock patches.
- Sveltia has entry locks, a viewer role and a takeover of its own, through its Additions service, for GitHub alone. With Forgejo none of it runs, and the lock stays the core's (ADR 0073).
- The Asset Library moves files between folders, from 0.267.0, and changes every entry that names one in the same commit, under no lock, as a rename of a file already did. Media is in no menu, and a patch sends its address to the list of entries, as Sveltia's own start, `/`, is sent (ADR 0063, Thomas, 2026-11-24). The patch moves as Sveltia's pages move, by the history alone, where Sveltia's start asks the browser for the new address.
- The Swedish has every text the British English has, *Restore Default* and *Clear All* among them.
- **The sign-in window.** Sveltia opens it at once, on the editor's own address, since Safari opens no window later than the click, and the editor that starts in it reads where to go and sends the window on to Forgejo, about 80 ms after its page has loaded. The editor is by then at work on other things, among them the icons it makes of its logo at every start: the logo as two pictures, each drawn, encoded and read with `Blob.arrayBuffer()`, at about the same 80 ms.
- **WebKit refuses whatever a page asks for once it has started for another,** until the other has answered: a `fetch`, and a read of a Blob too, which WebKit loads from a blob address it makes for the read, one that no `URL.createObjectURL` gave. It says of each in the console that it cannot be loaded "due to access control checks", which Playwright reports as an error of the page with its first characters gone: `ttp://localhost:<port>/<uuid> due to access control checks.` A blob address let go of before it is loaded gives another line, "Failed to load resource … WebKitBlobResource error 1", and one of another origin "Not allowed to load local resource". Chromium and Firefox refuse no such load; Firefox says of a font a leaving page was loading that it was stopped.
- So the two icons' reads were refused whenever the window left before them: in WebKit, in 11 of 66 openings of the window against a stand-in for Forgejo that answers in 300 ms, each line from the window's first page, a millisecond after a read; never from the page that opened it. With the window opened empty, nothing of the editor's is in it until Forgejo sends it back, and `acceptance/sign-in.test.js`, which failed in 15 of 16 runs in WebKit, passed in 24 in a row. A window its opener closes, as the editor closes this one once it has the token, was not seen to refuse a read.
